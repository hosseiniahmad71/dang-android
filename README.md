# دنگ Android v7 (نسخه آزمایشی ساخت APK)

این پروژه تبدیل نسخه ۶ دنگ به اپلیکیشن **مستقل و آفلاین اندروید** است. هدف، نصب APK با نام «دنگ» روی گوشی است، بدون Termux، سرور، اینترنت، Google Drive یا حافظه مرورگر.

**وضعیت تحویل: پروژه آماده ساخت، نه APK ساخته‌شده یا روی دستگاه آزمایش‌شده.** در محیط تولید این بسته، Android SDK، Gradle و شبکه دانلود بسته‌ها وجود ندارند؛ بنابراین `assembleDebug` در آن محیط اجرا نشده است. نسخه آزمایشی را قبل از ورود داده مالی واقعی آزمایش کنید.

## معماری

- ظاهر: React 19 + TypeScript + Vite، فایل‌های کامپایل‌شده داخل `android/app/src/main/assets/web/` بسته‌بندی می‌شوند.
- نمایش: WebView داخلی اپ روی آدرس مجازی `https://dang.local`، با منابع محلی و **بدون مجوز اینترنت**.
- داده: SQLite بومی اندروید در حافظه خصوصی `ir.dang.household`، نه IndexedDB، localStorage یا پایگاه داده مرورگر.
- منطق مالی: `src/native-runtime.mjs` با استفاده از `src/native-validate.mjs` و `src/native-ledger.mjs` کنترل حالت‌های مالی و سوابق را پیش از درخواست تراکنش بومی انجام می‌دهد.
- تراکنش: `DangDatabase.java` تغییر را با revision-CAS و تراکنش SQLite ثبت می‌کند و جدول‌های دفتر رویدادها، قراردادها و حسابرسی را نگه می‌دارد.
- بک‌آپ داخلی: فایل JSON مستقل در پوشه خصوصی برنامه + فهرست snapshot در SQLite، با حفظ حداکثر ۶۰ مورد؛ بعد از هر تغییر یا هنگام بازکردن برنامه طبق سیاست ساعتی/روزانه.
- بک‌آپ خارجی: فایل `.dangbak` رمزگذاری‌شده با AES-256-GCM و PBKDF2-HMAC-SHA256 (۳۱۰٬۰۰۰ تکرار)، ذخیره در مسیر انتخابی با Android Storage Access Framework. **این بک‌آپ خروجی رمزگذاری‌شده JSON است، نه خود فایل SQLite.**
- ارتباط چندگوشی و همگام‌سازی: در این نسخه وجود ندارد؛ هر نصب پایگاه داده مجزا دارد.

## ساخت APK با GitHub Actions (پیشنهاد برای کار با گوشی)

۱. در GitHub یک مخزن **Private** به نام `dang-android` بسازید. **از مخزن HamKar ERP استفاده نکنید**؛ این پروژه جداگانه است.

۲. فایل‌های داخل این پوشه را در ریشه مخزن قرار دهید؛ فایل workflow زیر باید در مخزن وجود داشته باشد:

`.github/workflows/build-apk.yml`

۳. در GitHub مسیر **Actions → Build Dang Android APK → Run workflow** را باز کنید. در صورت Push به شاخه `main` نیز workflow اجرا می‌شود.

۴. بعد از پایان موفق اجرای workflow، در بخش **Artifacts** فایل `Dang-v7-Android-debug-apk` را دانلود و استخراج کنید. داخلش `app-debug.apk` قرار دارد.

۵. APK را روی گوشی اندروید نصب و برنامه «دنگ» را باز کنید. از Settings مجوز «Install unknown apps» را فقط برای برنامه‌ای که از آن نصب می‌کنید فعال کنید.

**هشدار مهم درباره امضای APK:** `debug APK` برای آزمایش است. هر اجرای GitHub Actions ممکن است با کلید امضای آزمایشی جدید انجام شود؛ بنابراین نسخه‌های جدید احتمال دارد مستقیماً روی قبلی نصب نشوند. **قبل از حذف یا جایگزینی برنامه، از بخش تنظیمات یک `.dangbak` رمزگذاری‌شده در حافظه مستقل ذخیره کنید.** برای نسخه پایدار، کلید امضای release ثابت در GitHub Secrets تنظیم شود.

## ساخت با Android Studio در کامپیوتر

در پوشه ریشه پروژه:

```bash
npm install
npm run build:android
npm run test:native
```

در Android Studio، پوشه `android/` را باز کرده و **Build → Build APK(s)** را انتخاب کنید. JDK 17، SDK Android API 35، Gradle 8.10.2 و اتصال اینترنت برای دانلود وابستگی‌ها لازم است.

یا با Gradle:

```bash
cd android
gradle assembleDebug
```

مسیر خروجی: `android/app/build/outputs/apk/debug/app-debug.apk`.

## مهاجرت از دنگ ۶

**دیتابیس Termux خودکار به دیتابیس APK منتقل نمی‌شود.** برای انتقال امن:

۱. در نسخه ۶ فعلی، از تنظیمات «خروجی JSON» تهیه کرده و آن را در Downloads نگه دارید.
۲. APK مستقل را نصب و باز کنید؛ مطمئن شوید داده اولیه ساختگی/پیش‌فرض است.
۳. در تنظیمات APK، گزینه **مهاجرت / بازیابی JSON** را انتخاب و فایل نسخه ۶ را وارد کنید.
۴. گزارش مانده صندوق، تعداد رویدادها، اعضا و اقساط را با نسخه ۶ تطبیق دهید.
۵. قبل از استفاده اصلی، یک `.dangbak` رمزگذاری‌شده خارج از داده برنامه ذخیره و بازیابی آزمایشی آن را کنترل کنید.

داده‌های داخل `~/dang-data/dang.sqlite` نسخه ۶ به‌هیچ‌وجه توسط این پروژه دست‌کاری نمی‌شوند.

## تست‌هایی که واقعاً اجرا شده‌اند

```bash
npm run test:native
```

۸ تست موفق: صندوق، اعتبار کاذب، قفل ماه، سند برگشتی، تعدیل ماهانه، مانده تاریخی، بک‌آپ و سناریوی ترکیبی ۱۲ماهه. این‌ها آزمون موتور مالی JS با **شبیه‌ساز رابط بومی** هستند؛ جایگزین تست Java SQLite روی گوشی و تست نصب APK نیستند.

## محدودیت‌های باقیمانده

- ساخت Gradle/APK، تست WebView در گوشی واقعی، بازیابی فایل خارجی و آزمون Java/SQLite هنوز باید در محیط Android SDK انجام شوند.
- اعتبارسنجی کامل مالی در موتور JS بسته‌بندی‌شده اجرا می‌شود؛ سمت native نیز CAS و atomic commit دارد ولی به‌تنهایی تمام invariantهای دفتر مالی را بازاجرای مستقل نمی‌کند. برای استفاده مالی حساس، تست‌های یکپارچگی Android و حفاظت ورودی native باید سخت‌تر شوند.
- بک‌آپ‌های داخلی در داده برنامه قرار دارند و با حذف داده اپ یا پاک‌شدن گوشی حذف می‌شوند.
- نسخه Debug برای توزیع دائمی و ارتقای بی‌دردسر مناسب نیست؛ امضای Release ثابت لازم است.
- Google Drive و همگام‌سازی بین گوشی‌ها عمداً فعال نیستند.

**هیچ فایل APK واقعی تا اجرای موفق Gradle خروجی نخواهد بود.**
